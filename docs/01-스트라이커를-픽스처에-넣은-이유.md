# 01. Stryker 를 픽스처 안에 넣은 이유

픽스처 불변 원칙에 대한 예외다. 예외는 근거를 남기게 돼 있으므로 남긴다.

## 무엇을 바꿨나

`fixtures/sundaes` 에 추가한 것:

| 항목 | 내용 |
|---|---|
| devDependency | `@stryker-mutator/core@8.2.6` |
| devDependency | `@stryker-mutator/vitest-runner@8.2.6` |
| 신규 파일 | `stryker.config.json` |
| 스크립트 | `test:mutation` |

바꾸지 **않은** 것: 소스 파일 한 줄도, 기존 의존성 버전 하나도.

## 왜 루트에 두지 못했나

처음 계획은 Stryker 를 저장소 루트에 설치하고 설정으로 픽스처를 가리키는 것이었다.
픽스처를 아예 안 건드리는 쪽이 원칙에 맞으니까. 그런데 버전이 막았다.

| Stryker vitest-runner | 요구하는 vitest |
|---|---|
| 9.6.1 (최신) | **>= 2.0.0** |
| 8.2.6 | >= 0.31.2 |

픽스처는 **vitest 1.6.1** 에 고정돼 있다. 이건 사고가 아니라 결정이다 —
메이저 업그레이드(Vitest 1 → 3)는 픽스처를 흔들기 때문에 별도 실험으로 분리했고,
README 의 "고정해둔 것"에 그렇게 적혀 있다.

그래서 두 갈래가 남았다.

**갈래 1 — 최신 Stryker 를 쓰려고 vitest 를 2.x 로 올린다.**
픽스처의 테스트 러너가 바뀐다. 그러면 이 시점 이후의 모든 측정이 이전 커버리지 수치와
비교 불가능해진다. 뮤테이션 스코어를 재려고 비교 기준을 깨는 것이라 목적과 수단이 뒤집힌다.

**갈래 2 — Stryker 8.2.6 을 루트에 설치하고 vitest 도 루트에 따로 깐다.**
뮤테이션 러너는 픽스처가 쓰는 것과 **같은 vitest** 를 로드해야 같은 것을 측정한다.
루트에 vitest 를 또 깔면 두 벌이 생기고, 둘 중 하나만 올라가는 날 측정이 조용히 어긋난다.
불변 원칙이 막으려던 바로 그 사고를, 원칙을 지키려다 만드는 셈이다.

그래서 **Stryker 8.2.6 을 픽스처 안, 그 vitest 옆에 설치했다.** 러너와 테스트 러너가
한 트리 안에 있으면 버전이 갈라질 여지가 없다.

## 이 예외가 원칙을 훼손하지 않는 이유

불변 원칙이 지키는 건 두 가지다 — **소스가 그대로일 것**, **의존성 메이저 버전이 그대로일 것**.
이번 변경은 둘 다 건드리지 않았다. 측정 도구를 측정 대상 옆에 놓았을 뿐이고,
`npm ci → lint → tsc → test:coverage` 네 단계의 결과는 이전과 동일하다.

CI 의 `픽스처 불변 확인` 잡은 `fixtures/sundaes/` 아래 **모든** 변경을 막는다.
일부러 그렇게 넓게 잡았다 — 무엇이 "안전한 변경"인지 CI 가 판단하게 두면
판단 기준이 슬금슬금 넓어진다. 대신 사람이 라벨을 붙여 예외를 열고, 그 예외가
PR 목록에 남는다. 이 PR 에는 `fixture-change` 라벨이 붙어 있다.

## 무엇을 뮤테이션 대상으로 잡았나

`stryker.config.json` 의 `mutate` 는 앱 소스만 겨냥한다. 제외한 것과 이유:

| 제외 | 이유 |
|---|---|
| `src/pages/example/**` | 강의 연습용 컴포넌트. 아이스크림 앱이 아니다 ([`baseline-zero.md`](../reports/baseline-zero.md) 참고) |
| `src/setupVitest.ts`, `src/app/apiMockServer.ts`, `src/app/apiMockHandler.ts`, `src/shared/lib/testing-library-utils.tsx` | 테스트 하네스. 이걸 변형하면 "테스트가 테스트 하네스를 검증하는가"를 재게 된다 |
| `src/**/index.ts` | FSD 배럴 파일. 재수출뿐이라 변형할 로직이 없다 |
| `src/main.tsx` | 엔트리포인트 |
| `src/shared/type/**`, `src/vite-env.d.ts` | 타입 선언 |

**`apiMockHandler.ts` 를 제외한 것은 짚어둘 필요가 있다.** 여기에 [발견 3](00-베이스라인-발견.md)
(`immagePath` 오타)이 살아 있다. 하지만 이 파일은 목 서버의 응답 정의이지 앱 코드가 아니다.
뮤테이션 대상에 넣으면 "목 데이터를 바꿨을 때 테스트가 우는가"를 재게 되는데,
그건 테스트의 검증 강도가 아니라 목과 테스트의 결합도다.

발견 3 은 뮤테이션 스코어가 아니라 **에이전트가 이미지 `src` 를 단언하는 테스트를 쓰는지**로
평가한다. 두 지표는 서로 다른 것을 본다.

## 이 숫자를 읽을 때

뮤테이션 스코어는 커버리지와 **분모가 다르다.** 커버리지는 25개 파일 · 631 statement 기준이고,
뮤테이션은 위 제외를 적용한 앱 소스 기준이다. 두 백분율을 나란히 놓되 같은 척도로 읽지 않는다.

실제 값은 [`reports/baseline.md`](../reports/baseline.md) 에 기록한다.
